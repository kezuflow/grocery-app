## Phase 0 — Decide the first-release behavior and architecture

The owner requested customer ↔ Admin messages about an order, with an audible cue for new in-app notifications. The owner selected in-app sound only; browser push and email are outside this release. This is a new request beyond the earlier commerce-simplification exclusion of chat.

First-release behavior:

- One conversation per committed Order. Either the owning Customer or authorized Admin staff may begin or continue it, including after delivery or cancellation. No vendor/courier chat or AI-generated replies.
- Each message may contain bounded text and up to three private image/PDF attachments of at most 5 MiB each. Core validates bytes and owns the R2 key and D1 association. A file without text is allowed; empty messages are not.
- The first Customer message in a conversation atomically creates one clearly labeled automated acknowledgement from FreshMarkets. Admin can configure its bounded plain-text template; later Customer messages and Admin-initiated conversations do not create another acknowledgement. The acknowledgement promises only that the message was received, not a response time or an Order/refund outcome.
- Presence says whether the other side currently has this conversation open in a visible, connected tab; Admin is shown as a team, not a named staff member. Typing is a short-lived indicator for that same conversation. Neither signal is a persisted activity history or a delivery/read receipt. Loss of a socket removes the indicator after a bounded lease; hidden/closed tabs are not shown as present.
- Customer entry points: Account > Messages and each Order detail. Admin entry points: Orders > Messages inbox and each Order detail. The inbox shows latest activity and unread state; the thread shows sender and time, paginates older messages, and supports a bounded text composer.
- A message does not report an Order problem, resolve an issue, change fulfillment, approve a refund, or supersede staff-only support notes. Those workflows retain their existing authority.
- New incoming messages and existing in-app notification-feed updates play one short sound after the browser permits audio. An initial history load, a sender's own message, a replay, or the same event in another tab does not play again. Provide a mute control. Closed tabs receive no sound or push. Browser autoplay policy can prevent sound until the person interacts with the site.

### Approved 14-day retention policy

The owner shortened the window from 30 to **14 days after the last message** and chose to wait until the Order closes. A conversation becomes eligible only 14 days after the later of the last message and the Order's terminal close time. `DELIVERED` and `CANCELED` are the terminal Order states for this purpose; `EXCEPTION` and `CANCELLATION_REQUESTED` are not. An active related problem/refund/dispute or explicit, reviewed legal hold pauses deletion. A new message on an old Order starts a fresh conversation after earlier content is purged. Show the policy in the privacy notice; the owner's 2026-09-28 follow-up removes the paragraph from both thread composers. This is a product policy, not a statutory 14-day rule: the Philippine National Privacy Commission requires retention only as long as necessary for the declared purpose, legal claims, legitimate business purpose or law, and does not prescribe a universal period. Sources: [NPC implementing rules, section 19](https://privacy.gov.ph/implementing-rules-regulations-data-privacy-act-2012/), [NPC retention advisory opinion](https://privacy.gov.ph/wp-content/uploads/2022/01/NPC_AdvisoryOpinionNo._2017-024.pdf).

The existing 15-minute Core scheduler will run a bounded retention job to delete message **content and attachment bytes** in bounded, idempotent batches after rechecking eligibility. Keep only the minimum message identity, timestamp, actor kind, hash and audit/idempotency facts needed to prove that a send occurred and prevent a late retry from recreating purged text; never put text, file names or file bytes in audit, socket events, logs or long-lived command receipts. Design the transcript content and attachment associations as purgeable children of immutable message metadata. The authorized download endpoint denies access as soon as content is eligible for expiry, even if R2 deletion is retrying. No ordinary Customer/Admin delete endpoint is needed. Test a retention sweep racing a new message, reopening issue, refund or hold; deletion must fail closed or defer. A restore must rerun eligibility before serving restored content. Orphaned uploads that were never sent are removed after 24 hours through separate bounded cleanup.

Deleting from live D1 does not instantly erase its recovery history. D1 Time Travel can restore an earlier state for up to 30 days on Workers Paid (seven on Free); any separately exported backups need their own retention controls. R2 object deletion is separately retried until confirmed. The customer-facing notice must distinguish live-message expiry from backup expiry and avoid a promise of immediate physical erasure. Source: [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/).

### Decision table

| Option | Fit and cost | Decision |
| --- | --- | --- |
| Bounded HTTP polling | Smallest implementation. A 30-second interval produces 2.88 million requests/month for 100 tabs open eight hours daily; latency can reach 30 seconds. Indexes keep D1 row reads low, but every idle tab still calls Web/Core. | Reconnect fallback only. |
| WebSocket fanout using hibernating Durable Objects + D1 | Prompt updates while an app tab is open; idle sockets can hibernate without duration charges. The repository already has Web → Core authenticated upgrade forwarding and a hibernating `OperationalHub`, so this follows an established runtime pattern. Adds fanout/recovery code and a DO request per connection/publication. | Recommended primary transport. |
| Third-party hosted chat or WebSocket service | Adds account fees, integration and a second authority for sensitive Order/customer messages. | Not needed for this scope. |
| New D1 database or DO SQLite as message authority | A second D1 has no fixed fee advantage because D1 billing and included storage aggregate at account level. It would split Order ownership, IAM, audit and message writes across databases, losing the existing single-D1 atomic transaction boundary. DO SQLite is useful for socket coordination, not the canonical transcript. | Keep messages in existing Core D1. Revisit only on measured storage/throughput or isolation requirements. |
| Existing private R2 bucket, namespaced `messages/` objects | Reuses the Core `PRODUCT_MEDIA` binding while isolating object keys and authenticated access in code. Standard storage charges by actual GB-month and operations; deletes have no operation charge. Dynamic Order closure makes a fixed bucket lifecycle unsuitable. | Use the existing R2 bucket with Core-owned keys, private reads and a durable deletion queue. |

Cost model is illustrative, not an account bill: 100 concurrently open tabs × eight hours/day × 30 days ÷ 30 seconds = 2.88 million polls. At one connection per tab per day, sockets would create roughly 3,000 connection requests/month plus actual publication/reconnect traffic; real counts depend on tab churn. On Workers Paid, published included amounts are 10 million Worker requests/month, 1 million DO requests/month, 25 billion D1 rows read/month, 50 million D1 rows written/month, and 5 GB D1 storage. D1 is scale-to-zero and charges by rows/storage; DO hibernation avoids idle duration billing. Measure this account's actual baseline and query row metrics before and after staging. Sources: [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [DO WebSocket hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), [browser audio policy](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay).

Read-only production snapshot from `wrangler d1 info` on 2026-09-28: the existing Core D1 is 54.5 MB with 166 tables; the preceding 24 hours reported 34,277 read queries, 12,163 write queries, 2,353,086 rows read, and 36,747 rows written. In the illustrative 100-tab scenario, 30-second polling alone adds 96,000 requests and at least that many read queries per day, a material idle-query increase relative to this snapshot. A second database would not reduce account-level D1 usage. Typing/presence add only bounded WebSocket event traffic while a conversation is open, not D1 writes or inbox polls. R2 Standard currently includes 10 GB-month storage, 1 million Class A and 10 million Class B operations each month; above that, published rates are $0.015/GB-month, $4.50/million Class A and $0.36/million Class B, with free deletion and egress. Do not select Infrequent Access for potentially short-lived files because it has a 30-day minimum storage duration and retrieval charges. Source: [R2 pricing](https://developers.cloudflare.com/r2/pricing/). Reconsider D1 partitioning when measured storage approaches its per-database limit or query latency/overload shows a throughput bottleneck, with a plan for preserving Order/IAM authorization and audit integrity.

## Phase 1 — Durable message and authorization boundary

Add forward D1 migration in Core for `order_conversation`, immutable `order_message` metadata, purgeable `order_message_content`, `order_message_attachment` and durable upload/cleanup intents, per-actor read cursors, a reviewed retention hold, the acknowledgement template, and a recoverable publication revision/outbox. Index by customer/latest activity, Order/sequence, Admin latest activity, retention eligibility, and due publication. Keep one conversation per Order with a monotonic message sequence and bounded text. Do not copy address, phone, email, file names or file bytes into socket payloads, telemetry, audit or idempotency receipts.

Core owns typed `list threads`, `read thread`, `send`, `mark read`, `stage attachment`, `download attachment`, and `configure acknowledgement` commands/queries. Storefront resolves the active Customer from the session and proves Order ownership. Admin uses existing global `orders.read` for reads and `orders.manage` for writes, with active staff/scope rechecked in the D1 transaction. The committed Order and Customer relation are rechecked at write time. A send atomically commits the message, any first-Customer acknowledgement, attachment associations, conversation revision, per-audience publication intent, audit event, and immutable idempotency receipt. Failed authorization/guards leave none of these effects. Replays with the same key and payload digest return the same receipt; a changed payload conflicts. Reads use bounded keyset pagination and `private, no-store` Web adapters. Message text renders as plain text. Attachment uploads use individually bounded requests, byte signatures for JPEG/PNG/WebP/PDF, generated object keys, durable R2 intent, create-only retry and observation of unknown outcomes; never let an orphan become readable as a sent attachment. Downloads recheck current Order ownership or Global staff authority and return `nosniff`, a safe content disposition and private no-store headers.

## Phase 2 — Real-time hints and recovery

Add a `MessageHub` Durable Object using the Hibernation WebSocket API. Web forwards only same-origin upgrade requests to Core, as it does for the current Admin operational stream. Core authenticates and authorizes before a socket reaches a hub. Use a Customer-keyed hub for each Customer and a staff hub for the Global Admin inbox; send only a revision hint, never message body or Customer contact details. Add a conversation-keyed hub for ephemeral typing and presence. Its sockets carry only role/session attachment metadata and expire/reconnect for authorization refresh; a short lease and throttled heartbeats bound stale presence without D1 writes. Typing events are bounded, rate-limited, never persisted and expire quickly. HTTP/RPC through Core remains the only message/attachment write path, so socket loss cannot lose a committed message.

After D1 commit, publish each audience revision asynchronously. The existing scheduled recovery pattern retries unpublished revisions with bounded work; duplicate hints are harmless. Clients open one socket per visible signed-in surface, refetch authoritative pages on hint, reconnect with backoff, and catch up on open/reconnect/focus. Use a low-frequency read only while disconnected to bound missed-update delay. Close sockets on sign-out/access changes. A stale session cannot read message data because every refetch reauthorizes in Core.

## Phase 3 — Storefront, Admin and sound

Build Order-linked inbox/thread UI in both surfaces. Keep Storefront styling inside its existing design system; Admin uses the project `shadcn-admin` skill and its MessageScroller, Message, Bubble, Attachment and Marker compositions after inspecting CLI changes so shared primitives are preserved. Use the existing Storefront green tokens for Admin chat and shadcn semantic accents within `.fm-admin`; replace blue accents with green without changing Storefront or auth tokens. Preserve routes, Order actions, support notes and problem reports. Show presence, typing, automated acknowledgement, upload progress and accessible attachment links. Add loading, empty, retry, duplicate-send, lost-connection and permission states. Use semantic controls, keyboard access and a live region for arriving messages.

Add a shared client sound helper for newly observed incoming message identities and current customer/Admin notification-feed identities. Use Web Audio only after user activation, default audible with an explicit mute setting, and coordinate tabs to avoid duplicate sounds. Customer non-message notifications may need a visible-tab refresh because their current bell loads once; Admin location notices already receive operational WebSocket hints. No sound is promised when the browser blocks autoplay, the tab is closed, or the OS mutes the site.

## Implementation assumptions

The first release uses one conversation per committed Order, with either side allowed to start. Audio is limited to open, interacted-with tabs; browser push and closed-tab delivery remain excluded as selected. The owner has settled the retention trigger. These are the smallest coherent implementation choices for the requested basic feature; surface any material product-policy conflict discovered during implementation.

No additional provider account or second database is required for this plan. The sound and socket behavior still need actual browser verification.
