## Findings, highest impact first

1. **P1 — Production purchasing is on course to stay blocked after the original cutoff.** The five unresolved pre-cutoff payments are all exhausted and no longer selected by the scheduled lookup sweep; all have open attention cases. The fail-closed purchasing check is sound for uncertain money, but the currently available automatic path has stopped. Investigate provider lookup capability/availability and use the authorized Payments recheck or provider evidence to resolve each outcome before purchase. Do not infer failure from expired QR actions or edit payment rows directly. Evidence: [reconcile-stuck-payments.ts](../../apps/core/src/payments/application/reconcile-stuck-payments.ts), [scheduled-commitment-readiness.ts](../../apps/core/src/payments/infrastructure/d1/scheduled-commitment-readiness.ts), [create-procurement-requirement.ts](../../apps/core/src/procurement/application/create-procurement-requirement.ts), production aggregates above.
2. **P1 — Verified unpaid-window completion does not release purchase readiness.** Recovery can record `PAYMENT.UNPAID_WINDOW_CONFIRMED` and mark its lookup `COMPLETED` while leaving intent/attempt `REQUIRES_ACTION`. The shared purchase predicate still treats that canonical state and attempt as unresolved; its SQL does not consult the verified unpaid-window evidence. This is a liveness gap even when a future provider lookup gives the precise post-expiry waiting result. Existing tests prove the lookup conclusion and late-success legality separately, but do not prove purchase becomes available after that conclusion. The owner needs a consistent finality rule: either safely retire a verified unpaid commitment while specifying treatment of any later captured money, or allow bounded supplemental purchase for later valid commitments. Current PRODUCT explicitly permits late valid commitment, so simply ignoring attempts at cutoff would change policy. Evidence: [reconcile-stuck-payments.ts](../../apps/core/src/payments/application/reconcile-stuck-payments.ts), [scheduled-commitment-readiness.ts](../../apps/core/src/payments/infrastructure/d1/scheduled-commitment-readiness.ts), [PRODUCT.md](../product/PRODUCT.md).
3. **P2 — The operator path obscures the actual blocker.** The weekly banner says payments “are still being confirmed” even when all five have exhausted checks. Fulfillment links to Receiving, but this week has no receiving session because purchase has not been confirmed. Show distinct before-cutoff, actively-recovering, and exhausted-attention states in the typed Core weekly/fulfillment decisions, with a scoped Payments action for the latter and the purchase prerequisite before Receiving. Evidence: [scheduled-week.ts](../../apps/core/src/admin/application/scheduled-week.ts), [operational-order-detail.tsx](../../apps/web/components/admin/operational-order-detail.tsx), production pages above.
4. **P2 — Mobile Delivery weeks overflow horizontally.** The 390 px browser tests failed `documentElement.scrollWidth <= innerWidth`; the captured page shows the long Delivery week select extending beyond the viewport. Constrain the select and its flex item, then rerun the mobile summary and receiving checks. Evidence: [procurement/page.tsx](../../apps/web/app/admin/procurement/page.tsx), [scheduled-week.spec.ts](../../apps/web/tests/scheduled-week.spec.ts).
5. **P2 — A permanently blocked weekly page still polls D1 every five seconds per open tab.** The timer runs whenever `purchaseBlockedReason` is present, including `EXHAUSTED` cases that the scheduler will not automatically change. That is 12 reloads per minute per visible page, before measuring query rows. Use a change signal or bounded/backoff refresh tied to actual recovery state, plus explicit manual refresh for exhausted attention. Evidence: [procurement/page.tsx](../../apps/web/app/admin/procurement/page.tsx).
6. **P2 — `START_PACKING` can precede received goods.** Core applies the goods guard only to `MARK_PACKED`; this Order has already entered `PACKING` with zero accepted cycle goods. Per approved policy, that first transition closes customer self-cancellation even before the planned cutoff. This is internally consistent but a workflow risk; decide whether entering `PACKING` should require goods readiness or whether the UI should make the consequence explicit. Evidence: [advance-fulfillment.ts](../../apps/core/src/operations/application/advance-fulfillment.ts), [PRODUCT.md](../product/PRODUCT.md).
